---

Scope: post-init flexibility — three commands that together address the
v0.1.0 footgun we hit during the live walkthrough: *"`init` is one-shot,
recovery is destructive, MCP servers / tool installs after init are
unmanageable."*

The thesis: *"v0.1.2 made shipping clean. v0.1.3 makes switcher safe to
use day-to-day — broken init recoveries are no longer destructive."*

The three commands form one coherent narrative:

- **`uninstall`** — clean inverse of `init`. Walk every active link,
  replace each with a real copy of its target, optionally remove state.
- **`rescan`** — non-destructive pickup of tools installed *after* init,
  or newly registered TOMLs added to `<state_dir>/registry.d/`.
- **`prune`** — bulk cleanup of orphan profiles (saved but not active
  for any tool).

Together they obsolete the destructive-recovery procedure documented
in the v0.1.0 README. The procedure stays as an "if everything else
fails" escape hatch, but `uninstall` + `rescan` cover the realistic
recovery paths.

## Feature: `switcher uninstall`

**Today (v0.1.0):** There is no inverse of `init`. `pipx uninstall switcher`
removes the binary but leaves every managed live path as a dangling symlink
into a state directory the user no longer has tooling for. Cleaning up
manually requires the same multi-step procedure as the destructive-recovery
section in the README — but with the inverse intent.

**Proposed CLI surface.**

```bash
switcher uninstall                 # relink-only: every active symlink
                                   # becomes a real dir again; state stays
switcher uninstall --purge         # relink AND rm -rf <state_dir>
switcher uninstall --dry-run       # print what would happen, change nothing
```

`--purge` and `--dry-run` are independent flags (combinable: `--dry-run
--purge` previews both phases). Default is no-purge: saved profiles stay
on disk so `pipx install switcher && switcher init` can re-anchor against
them later.

**Per-tool unwind, mirroring `init` in reverse.** For each tool in the
active map, in order:

1. Resolve the live path's symlink to its target dir.
2. Copy the target into a sibling temp dir under the live path's parent
   (e.g. `~/.copilot.switcher-uninstall-tmp`).
3. Atomically swap the symlink for the temp dir via `Path.replace` —
   exactly the shape `swap_link` already uses for the forward direction
   (POSIX rename atomicity; Windows junction-recreate hedge).
4. Cleanup any stragglers.

Per-tool atomicity means a mid-run failure leaves you with either "still
a symlink" or "real dir" for every tool, never half-restored.

**Pre-flight before any mutation.** Same discipline `init` already has:

- Every entry in the active map must point at an existing profile dir.
- Every live path must be a symlink (or junction on Windows) — not a
  real dir or a regular file.
- Every symlink must resolve (no danglers).
- No orphan tool ids in the active map without a registered tool.

Fail loud before touching anything.

**Open design questions.**

- What about profiles that are saved but not active for any tool? They
  live in the state dir; without `--purge` they stay there. The
  `switcher prune` command in this same milestone handles that
  surgically — the two commands should pair cleanly.
- Should `uninstall` refuse to run if the active map references a tool
  whose builtin / user TOML has been removed since `init` (registry
  drift)? Lean toward "yes, error with the orphan tool id and instruct
  the user to either restore the TOML or `--force` past it." Better than
  leaving an unrestored live path silently.
- Should `--purge` confirm interactively by default (like `delete`)?
  Yes — destructive, mirror the existing safety pattern.

**Why this is a separate command from the destructive-recovery procedure.**

The recovery procedure documented in the v0.1.0 README is for "I'm stuck
in a bad state and need to escape." `uninstall` is for "switcher worked
fine, I'm done with it." Both intents are real; neither replaces the
other.

## Feature: `switcher rescan`

**Today (v0.1.0):** `init` is one-shot. Tools installed after `init`, and
newly registered tool TOMLs added to `<state_dir>/registry.d/` after
`init`, are not automatically picked up. The only recovery path is the
multi-step destructive procedure documented in the README.

**Walked manually during v0.1.0 testing.** Adding `gemini` via
`switcher tools scaffold` made it visible to `tools` and `list`, but it
remained unmanaged — the registry knows about it, but no profile contains
its config_subdir and the active map has no entry. The proposed
`uninstall` command (above) automates one half of the destructive
recovery; `rescan` automates the other half: picking up new tools without
losing existing profile state.

**Proposed CLI surface.**

```bash
switcher rescan                  # detect newly-installed tools and capture
switcher rescan --dry-run        # report what would be captured, change nothing
switcher rescan --only gemini    # explicit allow-list, mirror use --only
```

**Per-tool capture, additive only.** For each registered tool whose
first config dir exists at the live path AND whose id is not in the
active map:

1. Pre-flight: live path must be a real directory (not a symlink, not a
   regular file, not a junction). Fail loud before any mutation.
2. Move every live config dir for the tool into
   `<state_dir>/profiles/<dated-current>/<config_subdir>/` (the
   dated-current dir = the active profile per `status`).
3. Replace each live path with a symlink/junction into the snapshot,
   exactly as `init` does.
4. Update the active map: `active[tool_id] = <dated-current>`.

`rescan` is **additive only**. It never removes anything from the active
map, never modifies a tool already under management, never overwrites
profile content. This is the safety contract that justifies the lack of
backup-before-running.

**Pairing with the v0.1.4 init `--skip` / `--only` flags.** A tool the
user explicitly skipped at `init` time still gets caught by `rescan`
unless it stays out of the registry. That's the right default —
`--skip` is a one-shot intent at init time, not a permanent exclusion.
Users wanting a tool permanently out of switcher's view should remove
its registry TOML (or rely on the absence of its first config dir).

**Open design questions.**

- Should `rescan` capture into the dated-current profile, or into a
  fresh profile (`<dated>-rescan-<n>`)? Lean toward dated-current —
  matches `init`'s shape, and keeping all "currently captured" content
  in one profile is the conceptual model the README sells.
- What if a previously-managed tool's TOML is removed from the registry
  (orphan in the active map)? Today, `service.rename` already handles
  the "orphan in active map" case for re-pointing. `rescan` should not
  touch orphan entries; emit a warning instead. (A future
  `switcher unmanage <tool>` could be the explicit removal path.)
- Should `rescan` honor `init`'s pre-flight "AlreadyLinkedError" for the
  live paths it's about to capture? Yes — same discipline.

## Feature: `switcher prune`

**Today (v0.1.0):** `delete` removes one named profile at a time and
refuses if the profile is active for any tool. Bulk cleanup of
"profiles I created during experimentation and forgot about" requires
either repeated `delete` calls or manual `rm -rf
<state_dir>/profiles/<name>/`. The latter bypasses the active-profile
guard and silently leaves a stale entry in the active map if the
deleted profile was active.

**Walked manually during v0.1.0 testing.** After a 5-minute
walkthrough we accumulated `vanilla`, `2026-05-06-current`,
`before-experiment`, `experiment` → `client-A`, plus the
gemini scaffold. Half of those were demo artifacts. The destructive
recovery procedure also implicitly creates "orphan" profiles when
restoring named profiles from backup that aren't being made active.

**Proposed CLI surface.**

```bash
switcher prune                   # interactive: list orphan profiles, confirm
switcher prune --dry-run         # list orphan profiles, change nothing
switcher prune --force           # delete all orphan profiles, no confirm
```

**Definition of "orphan profile."** A profile in
`<state_dir>/profiles/` that is **not** referenced as the active profile
by any tool in the active map. The dated-current profile, vanilla,
and any profile a user has switched to via `use` are protected by the
active-map check — same shape as the `delete` active-profile guard.

**Atomicity per profile.** Iterate the orphan list; for each, call
`store.delete(<name>)` (the existing v0.1.0 path that already handles
metadata removal and rmtree). A mid-run failure leaves earlier deletions
done and later ones pending; safe to re-run because the orphan check is
recomputed each invocation.

**Why a separate command from `delete`?** `delete` takes a name and
errors if it's wrong; `prune` takes no name and operates on a derived
set. They're different intents. Bundling them as `delete --all-orphans`
muddies the safety story — `--all-orphans` could be combined with a
positional name in surprising ways.

**Pairing with `uninstall --purge`.** `uninstall --purge` (above) wipes
the entire state dir. `prune` is the surgical alternative: keep
switcher installed, keep your active state, just clean out the
orphans. They share no code path; both call into `store.delete()`.

**Open design questions.**

- Should `prune` interactive mode let the user select which orphans to
  delete (multi-select prompt), or all-or-nothing? Lean toward
  all-or-nothing — keeps the v0.1.3 prompt surface minimal. Users
  wanting selective deletion can still use `switcher delete <name>`.
- Should `prune` print the disk usage of orphan profiles in dry-run
  output? Useful but adds a `du -sh` per profile. Probably yes, gated
  by `--show-size` flag to keep default output fast.
